# Passwordless parent and learner devices — development draft

Status: design and mock-tested client only. The 004 SQL has NOT been applied, anonymous sign-ins have NOT been enabled, Google OAuth has NOT been configured, and the code is NOT on the production site. Do not merge until a security review and real two-device end-to-end testing have passed.

Parent verifies identity with Google OAuth. A successful Supabase Auth session is registered by server-side function, restricted to a signed-in non-anonymous Google principal with an existing Auth session. The parent issues a 256-bit, single-use, 15-minute invitation. An anonymous child signs in with Supabase Auth, then redeems the invitation. The server records child user ID, parent ID and exact Supabase session_id. Refresh preserves the session. RLS checks the registered, non-revoked session and its relationship on every protected data request; parent can edit plans but cannot write learner results.

Learner identities are stable private rows, separate from anonymous Auth users. A parent may issue a replacement-device invitation for the existing learner, preserving past records. A pre-cloud local backup remains intact until explicitly bound, and outbox items use stable UUIDs for retries. Legacy rows are backfilled into the stable identity table in draft migration.

A parent can mark a child or own parent session as revoked, immediately blocking application data access through RLS. This does not itself revoke the Supabase refresh token and cannot erase data already stored on a lost device. For loss of a parent device, also revoke the Google account session. Device screen locks remain essential. Official Supabase Auth signOut({scope:'local'}) is used when the device itself signs out; remote Auth refresh-token revocation remains unsolved and must be completed or explicitly accepted before release.

Anonymous sign-ins are disabled until abuse prevention (such as CAPTCHA), quotas, and RLS are reviewed. Parent OAuth requires an authorized Google Cloud client, configured Supabase provider, and tested redirect. Never place a client secret or service role key in the site. Child browser storage clearing means anonymous Auth session is lost; parent must approve a replacement device. No password is required in ordinary use, but Google can request reauthentication or verification when its session is absent or expired.

Mock tests cover parent routing, child enrollment, legacy data, parent-plan propagation, and revoke UI. SQL outer syntax parses but PL/pgSQL bodies, real RLS, sign-ins, refresh/revocation, email-free recovery, concurrency, offline delivery and two separate Android devices still need real testing. Permission-boundary tests must cover unauthorized invitations, expiry/replay, cross-parent access, revoked issuer/session, role spoofing, token expiration, and stale Auth sessions. Do not alter auth.users, auth.identities or auth.sessions directly to create test identities; use official supported test flows.
