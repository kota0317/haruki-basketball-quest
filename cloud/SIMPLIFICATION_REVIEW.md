# 単一家族向けの簡素化メモ（下書き実装・実環境未検証）

PR #1 は本番公開しない。既存の 005 は本番に適用されていない。以下の方針は 005 の下書きに反映済み。本メモは migration ではない。

## 目的

既存の hq_parent_links、hq_learning_events、hq_study_plans の列と auth.users を参照する外部キーを維持し、端末ごとの匿名 Auth ID と既存の学習者 ID を安全に対応させる。学習者 ID が auth.users の削除に連動して削除される現行の外部キーは維持するため、旧 Auth ユーザーを削除しない運用が必要。匿名ユーザーの自動削除設定および復旧時の保持期間を実環境で確認すること。

## 端末登録の下書き

- 初回保護者：匿名 Auth 後、管理者が Supabase 管理画面でそのセッションを確認し、承認する。公開コードや固定 URL は承認権限を与えない。
- 初回学習者：承認済み保護者が 256 bit のランダムコードを発行。コードは期限付き・一度限りで、ハッシュのみ保存。原子的に消費し、紐付ける。既存 hq_private.invites の再利用可能性を検討する。
- 再登録：保護者は管理画面の再承認、学習者は保護者の再招待。古い学習者 ID を新端末に結び付ける。旧端末のクラウドアクセス停止を可能にする。
- 新しい private 端末登録表に認証された principal ID、JWT session ID、役割、対応する既存の parent ID / learner ID、停止状態を記録。匿名セッション自体には権限を与えない。ユーザー申告や user_metadata で権限を決めない。

## 必須の変更と安全性

既存 RLS は auth.uid() をそのまま学習者 ID として扱っているため、再登録後の新しい匿名 Auth ID では既存学習者の記録にアクセスできない。認証済み・停止されていない端末の対応表を使う RLS と、保護者だけにメニュー編集を許すポリシーが必要。旧招待 API の権限も同時に安全に無効化する必要がある。現行のポリシーをそのまま残すだけでは、停止端末の遮断や保護者専用編集は保証できない。

005 の household / learners テーブルと既存外部キーの置換は、この案では不要となる見込み。ただし既存 ID を Auth ユーザーに依存させるため、ユーザー削除時の連鎖削除・匿名ユーザー整理・復旧・旧セッション残存が運用上のリスクとなる。コード・RLS・実際の Auth と API の検証が必要。端末停止はアプリのクラウドデータのアクセス遮断であり、Auth のリフレッシュトークン無効化や端末内データの遠隔消去ではない。

## 公開前の条件

1. 対象テーブル、制約、RLS、関数、権限、データの確実なバックアップと復元手順を準備し、復元可能性を検証する。端末内記録も初回同期確認まで保持する。
2. 本番には未検証の RLS を適用せず、実 Supabase Auth と本番同等 RLS で、承認、期限、再利用、第三者拒否、保護者の成績変更拒否、端末停止、既存データ保持、ネットワーク障害後の再送を検証する。
3. 保護者のメニュー変更と学習者の学習記録を異なるセッションで往復確認し、Android 実機の結果を分けて記録する。
4. 合格後に既存 PR を更新し、マージ、Pages 公開状態を検証する。

本番に適用されている 001–003 は異なる権限モデルである。匿名 Auth を有効化するだけでは本案は実現しない。
