# Supabase owner-approved parent device — draft only

No Google OAuth, Google Cloud project, custom SMTP, app-level passwords, or bootstrap bearer secret is used. Both devices receive official Supabase Auth anonymous sessions. A session alone grants no app data access.

Initial parent setup and parent recovery: the parent device requests an expiring random request ID. It is an identifier, not a credential and cannot authorize a device on its own. The authenticated Supabase project owner verifies that the ID is displayed on their own parent device, and executes the displayed approval SQL in their own project's SQL Editor. The owner-only function checks that the request was created from an Auth-issued JWT and has not expired, consumes it once, and creates a parent device grant. A new parent device always requires a fresh administrator approval. No Supabase Auth internal table is read or modified. No secrets or service-role keys go in client code. Parent device loss requires Supabase owner access again; losing Supabase owner access has no in-app recovery.

A parent device issues a random 256-bit, 15-minute one-time child invitation. A child redeems it only after signing into an anonymous Auth session. The original learner Auth user ID remains the stable learner ID. A parent can approve a replacement child session without moving past records; the original Auth user must not be deleted because existing foreign keys cascade on deletion. The parent's active session that created the invitation must not be revoked at redemption. When browser data is cleared, the anonymous session is irrecoverable: the owner approves a new parent device or a registered parent invites a replacement child device. Ordinary use persists and refreshes sessions automatically via official Supabase SDK.

Device-scoped RLS denies app data to unapproved, unlinked or revoked sessions. Parents may edit plans but may not insert/update/delete learner events. Revocation immediately cuts app data access; the Supabase refresh token itself is not remotely revoked, and offline data cannot be erased from a lost device. Keep the device screen lock enabled. Parent account expiry and browser data clearing require project-owner reapproval. Abuse prevention and reasonable Auth rate limits must be configured before enabling public anonymous sign-in; an internet-exposed signup endpoint can create many accounts.

005_owner_approval_draft.sql must REPLACE the unapplied Google-based 004 draft, never run both. It is unapproved, not applied to the deployed project. The simplified draft preserves public table rows and the original Auth foreign keys; it rejects ambiguous legacy data with multiple learners or parents. The original parent and learner Auth users must be retained. Migration must be backup-protected and tested against the real schema and existing data. Existing 003 invitation functions are disabled by 005. Tests simulate the Supabase auth schema only in an isolated local PostgreSQL (PGlite), not the real Supabase auth system. Local tests cover an approved parent, unauthorized approvals, expired/replayed requests, child enrollment, unauthorized data access, parent edit and event-write denial, revocation and replacement devices. Client tests use mocks. Real Supabase Auth, API behavior, session refresh, remote refresh-token revocation, separate Android devices, CAPTCHA and production release remain unverified.
